# Raw capture

A session can write the raw venue bytes it receives into time-partitioned MDC1 files with one manifest per directory. Replay of such a file reconciles the config against the file's own header.

[[mdc]] describes the container itself.

## Capture taps

[[crates/datafeed/src/tap.rs#CaptureTap]] is the seam a session drives at one point: raw venue bytes before the adapter.

Raw capture is the replay source of truth, so an adapter re-run over it reproduces the normalized stream. Capturing that stream a second time earned nothing and was dropped.

[[crates/datafeed/src/tap.rs#NoopTap]] is the default; [[crates/datafeed/src/tap.rs#MdCaptureTap]] holds one lazily opened per-window `md_capture::RawWriter`. [[crates/datafeed/src/tap.rs#AnyTap]] is the enum `wiring.rs` selects at assembly time: the trait is object-safe now that the generic record method is gone, but a vtable hop per frame buys nothing over a two-variant match.

`raw_dir` drives the tap. [[crates/datafeed/src/wiring.rs#build_tap]] runs `NoopTap` when it is unset and an `MdCaptureTap` when it is set, parsing the `partition` token to a window interval. On replay the source file already is the raw feed, so capture is redundant and left off. A config still setting the retired `normalized_dir` is refused rather than ignored: it used to gate the whole tap, so accepting it silently would turn capture off.

A relative `raw_dir` resolves against the directory the binary starts in. `out/` is gitignored at the workspace root and in the crate directory, so the README's `./out/raw` root stays out of git from either one; any other root inside the repository is not ignored.

Each dir is a bucket root, not a file: the tap derives its own tree and self-describing leaf names (see [[capture#Storage layout]]), so a run never names its own output. Writers open lazily, never truncate an existing file, and close on window roll, bounding open handles to one; a record whose window regressed to an already-closed one is an ordering violation and errors. `finish` flushes the open zstd frame (the writers carry no `Drop` auto-finish), and that close writes the dir's manifest, so [[crates/datafeed/src/feed.rs#FeedSession#close]] calls it, and the binary closes its session on every exit, errors included; a live session reaches it on the shutdown stop flag (see [[session#Session hot loop and record routing#Graceful shutdown]]), so only a hard kill leaves the in-progress window unflushed. A multi-day live session rolls the whole date dir when a frame's `ts_recv` reaches the end of the open session under the venue's `session` model (New York midnight for NASDAQ, a fixed UTC offset for a `DailyFixed` venue, UTC midnight for a continuous one): the completed day's writer finishes and its close writes that day's last `manifest.json`, so a crash loses at most the in-progress window. The first frame seeds the open session, so a single-session replay never rolls. A frame before the open session's start errors (`DayRegression`), the day-level analogue of the window-regression guard, and a frame the session model cannot place (an unknown zone) errors with `SessionUnresolved`. A session that opens before the epoch starts at `0`, so a synthetic replay stamped from `0` still lands in its first session. Only that epoch session clamps; any other anchor that does not resolve is `SessionUnresolved`. The regression check runs before any zone lookup.

The trade date names the output dir and stamps the container header. On live, `capture_date` stays unset and the tap takes the first frame's session label, so a supervisor restart on a later day writes that day's dir instead of the stale configured one. [[crates/datafeed/src/wiring.rs#build_tap]] refuses a set `capture_date` on a live source, since a date fixed in config goes stale after the first day roll. On replay a synthetic `ts_recv` dates nothing, so the date comes from the MDC1 header (the reconcile fills it) or config, and a replay tap with it unset is an error.

## Storage layout

Raw output is partitioned by time window into self-describing MDC1 files under a bucket root, and every directory carries a manifest.

The day is the venue's trade date: the first frame's session label on live, or `capture_date` on replay (the MDC1 header or config), seeds it, and the tap advances it by the session-label day delta when a frame's `ts_recv` crosses into the next session ([[crates/datafeed/src/tap.rs#MdCaptureTap#enter_session]]). Session bounds come from the descriptor's `session` model (`md_pipeline::SessionModel`, see [[pipeline#Venue adapter seam#Session model]]) through [[crates/datafeed/src/session_window.rs#resolve_session]]: `session_label` places the frame and `resolve_anchor` gives the `[start, end)` anchors, once per session and never per frame. That function and the `YYYYMMDD` day arithmetic live in their own module, apart from the tap, so any caller that rolls on the venue trade date shares one window rule. Zoned venues resolve through `md_pipeline::BundledTzdb`, which reads only the bundled IANA db, so a replay anchors the same on every host. NASDAQ rolls at New York midnight, so its sessions span 23h and 25h on DST transition days. One session is one date dir, and a non-UTC session is never split across two UTC days.

Under a day partition (`1d` or longer) the window is the session itself, so a 25h fall-back session stays one file instead of spilling its last hour into a phantom window. A sub-day partition floors the frame's offset from the session open (`ts_recv - start`, never negative since the open session holds the frame) to the interval, driving the writer roll in [[crates/datafeed/src/tap.rs#MdCaptureTap#ensure_raw]]. [[crates/datafeed/src/wiring.rs#capture_dir]] lays out `<root>/<venue>/<version>/<YYYY-MM-DD>/` from the venue descriptor's `tag`, `version`, and the trade date; [[crates/datafeed/src/wiring.rs#capture_filename]] derives the leaf `<venue>_<version>_<window>.mdc1.zst`, where [[crates/datafeed/src/wiring.rs#window_label]] is the trade date plus, for sub-day partitions, that session-relative offset (`Thh`, `ThhMM`, `ThhMMSS`) so adjacent windows never collide. The offset does not wrap at 24h: a fall-back session's 25th hour is `T24`, not a second `T00` that would truncate the first. The version is proto-independent, so a dual-channel venue is one version.

A window file is never truncated. The writer opens with `create_new`, so a run that starts inside a window an earlier run already wrote (a live restart; under `1d` that is the whole session) takes the next free part, `<venue>_<version>_<window>_r<N>.mdc1.zst`, and the earlier file keeps its bytes.

The window interval is the `partition` duration token (`1d` default; `1h`, `30m`, ... roll on the boundary). Sub-day partitions assume the raw stream is monotonic in `ts_recv`; `1d` never rolls intra-session and is always safe.

[[crates/datafeed/src/tap.rs#MdCaptureTap#record_closed]] rewrites the dir's `manifest.json` through [[crates/datafeed/src/tap.rs#write_manifest]] every time a file closes, on a window roll, a day roll, or [[crates/datafeed/src/tap.rs#MdCaptureTap#finish]]: venue, version, partition, and one entry per file (window, leaf name, record count, sha256). Entries sort by name so the manifest is byte-stable across replays. A rewrite costs the whole manifest, which stays small for partitions of a minute or longer (1440 entries a day at `1m`). Before its first file in a dir, [[crates/datafeed/src/tap.rs#MdCaptureTap#stage_existing_manifest]] stages the entries of any `manifest.json` already there, so a restarted run's manifest lists the earlier run's files beside its own instead of replacing them. An existing manifest under another partition is refused (`ManifestPartition`) before any byte is written, since one manifest names one partition. One that does not parse is renamed to `manifest.json.corrupt` with a warning and the run indexes only its own files, so a torn manifest costs the earlier entries (the files stay, and their counts and hashes can be recomputed) and never ends the session. The flush writes `manifest.json.tmp`, syncs it, and renames it over `manifest.json`, so a kill, full disk, or power cut mid-write leaves the previous manifest whole. A hard kill leaves only its in-progress file out of the manifest, since every window it closed was listed at the close, and the next run never overwrites that file.

## Capture header reconcile

On MDC1 replay the capture carries its own venue and date, so the config need not repeat them. [[crates/datafeed/src/app.rs#run_config]] peeks the header before building the tap and reconciles config against it.

[[crates/datafeed/src/replay.rs#peek_capture_meta]] reads the 16-byte MDC1 header ([[mdc#Container header]]) without decoding the zstd body, returning `(venue, date, feed)` for a capture container and `None` for any other format or unreadable path. [[crates/datafeed/src/app.rs#reconcile_capture_meta]] then fills an unset (`0`) `venue_id`/`capture_date` from the header and rejects a set value that disagrees, so a stale config never silently mislabels output. An unset (`0`) `session_midnight_ns` then becomes the resolved trade date's anchor under the descriptor's `session` model (`SessionModel::resolve_anchor` through `BundledTzdb`, for NASDAQ the DST-correct New York midnight), the base the adapter adds message offsets to. An explicit nonzero offset wins, and a date that does not resolve leaves it manual rather than failing startup. Live has no header to read, so there an unset offset turns on the per-date roll instead and a set one is refused at startup (see [[session#Session hot loop and record routing#Live adapter anchor roll]]). The tap does not read this offset: it resolves its own session anchors (see [[capture#Storage layout]]).

The header feed byte separates feeds that share a `venue_id`. Without it the reconcile would pass one feed's capture under the other feed's config, and the wrong adapter would drain almost nothing (a full replay ending near 0 records, exit 0). `reconcile_capture_meta` rejects a nonzero header feed that disagrees with the configured venue's own `feed_id` ([[crates/datafeed/src/venue.rs#VenueDescriptor]]) before any replay runs. A legacy capture written before the feed byte reads feed `0` and makes no such claim; there [[crates/datafeed/src/app.rs#check_replay_path_feed]] falls back to the self-describing leaf name (`<venue>_<version>_<window>...mdc1.zst`), failing fast when the filename disagrees and running unguarded when it is off-layout.
