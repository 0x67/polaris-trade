# Session wiring

One binary runs one venue market-data session, live or replay, selected by config, and a host embeds the same session. The hot loop, book and derive routing, egress sequencing and capture taps are the same for all.

## Config-driven venue selection

[[crates/datafeed/src/config.rs#DatafeedConfig]] picks a venue by name (`nasdaq` is the one built-in) and a source (`Live`, `LiveDual`, `Replay`). [[crates/datafeed/src/feed.rs#FeedSessionBuilder#build]] dispatches on the source kind alone, never on the venue.

The venue name resolves against [[crates/datafeed/src/venue.rs#VENUES]], the built-in descriptor slice, while the config loads, so an unknown venue fails at startup. The resolved [[crates/datafeed/src/venue.rs#VenueDescriptor]] carries the venue's storage `tag`, feed `version`, MDC1 `feed_id`, trading-day `session` model, ingest `streams`, whether it runs live over SoupBinTCP (`soupbin_live`), and a `make` constructor as data. Adding a venue adds a descriptor in `venue.rs` and no glue module. Descriptors have no `PartialEq`: identity is the name, since comparing the `make` fn pointer is unpredictable.

`make` builds the venue's adapter from the config as a `Box<dyn md_pipeline::DynAdapter>`. Live and replay both build through it and run [[crates/datafeed/src/session.rs#step]], so venue dispatch is one fn-pointer call per session. The `venue.rs` unit test `builtin_descriptors_agree_with_their_adapters` pins each built-in descriptor's `session` to what its adapter declares, and its `streams` to the adapter's as a set: an adapter's `streams()` carries no order, while the descriptor's order is a contract of its own (below).

Descriptor data, with no match on the venue, decides which sources a venue accepts. [[crates/datafeed/src/live.rs#live_dial]] takes `Live` for a SoupBinTCP venue with one stream and `LiveDual` for one with two, and `LiveFeed::new` ([[crates/datafeed/src/live.rs#LiveFeed]]) refuses any other pairing when the session builds ("unsupported venue/source combination"). The same `streams` slice that picks the shape supplies the ids each live leg tags its frames with, so arity and ids cannot drift apart. The order of `streams` is positional: the first id tags the primary leg and the second the secondary leg, and the first is also the session's trade aggregate stream (see [[session#Session hot loop and record routing]]). The `live.rs` unit test `live_dial_tags_each_leg_with_its_descriptor_stream` runs a one-stream and a two-stream descriptor with ids other than 0 and 1, gives the two legs distinct endpoints, and checks each leg's endpoint and id, so a swapped pair or a literal id inside `live_dial` fails it. The test never reaches `LiveFeed::dial`: a literal id at its call site leaves the bound `stream` or `streams` unused, and clippy's `-D warnings` gate rejects that.

NASDAQ sets `soupbin_live: false`: TotalView publishes over MoldUDP64, which has no live source here, so NASDAQ stays replay-only and no built-in venue runs live today. The `Live` and `LiveDual` paths stay in the binary for a descriptor that sets the flag, and tests build such descriptors from `NASDAQ` (see [[tests#Unit tests on the NASDAQ fixture venue]]). `ReplayFeed::open` ([[crates/datafeed/src/replay.rs#ReplayFeed]]) refuses a multi-stream venue on any container but `Capture`, the only one that tags rows with their stream.

The command-line `main.rs` owns only argv, error display, and exit status. `app.rs` owns config loading and the binary's run; `feed.rs` owns the session and its builder, which dispatches on the source; `live.rs` owns reconnecting socket sessions; `replay.rs` owns container/pacing assembly; `wiring.rs` owns sink and capture construction. [[crates/datafeed/src/app.rs#parse_config]] picks the decoder by file extension: `.json` is strict JSON, `.yaml`/`.yml` (and any other extension) is YAML, the default format. `config.example.yaml` is the commented option reference; the live `config.yaml`/`config.json` is gitignored inside the crate directory so endpoints and credentials stay out of git.

A dual-channel venue (a primary order-flow channel plus a secondary enrichment channel) takes `LiveDual` with two TCP endpoints; a single-channel venue takes `Live`.

## Logging and diagnostics

The binary installs exactly one `tracing` subscriber at startup; the session code emits events and never prints. [[crates/datafeed/src/app.rs#run_config]] picks the sink by whether an observability config is present.

With an observability config, logs route through the metrics pipeline as machine-scrapeable Json on stdout; otherwise `obs::init_fallback_logging` installs a stderr `fmt` subscriber honoring `RUST_LOG` (default `warn`). A config that requests observability in a build without the `observability` feature is a startup error.

Session-end stats log at `info`, forced reconnects and rejected resumes at `warn`, a closing socket error at `error`. Structured fields (`venue`, `stream`, `?stats`, `%err`) stay filterable and become OTLP attributes when the pipeline is on.

## Live and replay IngestSource swap

Both deployment tiers implement `md_pipeline::IngestSource` ([[pipeline#Ingest]]), so the session functions below never know whether they are driving a socket or a file.

- Live: [[crates/datafeed/src/source.rs#LiveSoupBinSource]] wraps one `client_soupbintcp::SoupBinClient` and drives its non-blocking `poll` in a loop (sync busy-poll, no `.await` on the hot path). [[crates/datafeed/src/source.rs#DualLiveSource]] merges two of these for a dual-channel venue, each leg tagging its frames with the stream id the venue descriptor declares for it. Every yielded [[crates/datafeed/src/source.rs#LiveFrame]] stamps `venue_seq` from the client's own `Frame::sequence()`, the exact SoupBinTCP session sequence, never a counter the adapter invents.
- Replay: `md_replay::BinaryFileReplay` (length-prefixed venue dumps, always `StreamId(0)`), `md_replay::PcapReplay` (classic pcap, packets verbatim), or `md_replay::CaptureReplay` (the [[mdc]] zstd container, which carries a real per-row stream id and is the only replay format that can drive a multi-stream venue). [[crates/datafeed/src/config.rs#ReplayFormat]] selects one, or `Auto` sniffs the container via `md_replay::detect_container` (magic bytes, extension fallback; unknown input refuses startup).

A live source that decodes frames before observing a transport close returns that partial batch first and reports `Closed` on the next receive. This prevents the reconnect boundary from silently dropping already-buffered venue events; the dual source applies the same rule when its second leg closes after the first produced frames.

### Heartbeats and server silence

The live source sends client heartbeats and ends a session when the server has sent nothing for too long, both from the same `poll` call that reads frames.

Each `poll(now)` of the SoupBinTCP client ([[soupbintcp#Synchronous API]]) flushes pending writes and, while streaming, sends a client heartbeat once nothing is queued and `heartbeat_interval` (default 1 s) has passed since the last send. When the socket drains with no message and the server has been silent past `heartbeat_timeout` (default 15 s), the client closes its session and yields `SoupBinEvent::HeartbeatTimeout`; the next `poll` returns `SoupBinError::EndOfSession`. Both durations come from the `soupbin` block of the source config.

In `recv_batch` of [[crates/datafeed/src/source.rs#LiveSoupBinSource]] the heartbeat events (sent, received, timeout) are not data frames and are skipped. The `EndOfSession` error after a timeout closes the source the way a transport close does: frames already collected in that call return first, and the next call reports `Closed`. `LiveFeed::advance` ([[crates/datafeed/src/live.rs#LiveFeed]]) then captures the resume point and reconnects (see [[session#Restart and resume seam]]).

Both behaviors arrived with the move onto this workspace's client. The datafeed's earlier client call only read the socket, which left client heartbeats unsent and let a session wait indefinitely on a server that had stopped sending.

### Connect timeout

A live dial has 5 s to complete. Past that it fails, and the live run ends with that error.

[[crates/datafeed/src/source.rs#connect_tcp]] dials through `transport_socket::tokio::TcpStream::connect` with `TcpConfig::new(endpoint)`, whose `connect_timeout` defaults to 5 s ([[socket#Socket types and configs]]). Expiry maps to `TransportError::Connect` with `TimedOut` and reaches the caller as `SourceError::Transport`. `LiveFeed::dial` ([[crates/datafeed/src/live.rs#LiveFeed]]) treats it like a refused dial: a connect error is not retried and ends the session, and the binary closes the session, finishing the capture, before the error propagates. The earlier transport had no bound of its own and waited on the operating system.

A set stop flag still ends a dial early. [[crates/datafeed/src/source.rs#connect_tcp_resuming]] and [[crates/datafeed/src/source.rs#connect_dual_resuming]] poll it every 50 ms while a dial is outstanding and drop the dial on shutdown.

### Replay load mode, pacing, and clock

Replay arms wrap every container in `md_replay::PacedSource` and stamp egress from `md_replay::SharedClock`, so replay `ts_egress` derives from replayed `ts_recv`, never wall time.

[[crates/datafeed/src/config.rs#LoadMode]] picks materialization: `Stream` (default, constant memory) or `Eager` (`from_path_eager`/`from_gz_eager`, whole file slurped and inflated up front, isolating pipeline cost from io in benchmarks). `Eager` with `Capture`/`Pcap` is a wiring-time error; those readers have no streaming/eager split yet.

[[crates/datafeed/src/config.rs#PacingConfig]] carries a default mode plus optional `ts_recv` windows ([[crates/datafeed/src/config.rs#PaceWindowConfig]], each with its own [[crates/datafeed/src/config.rs#PacingModeConfig]]). `replay.rs` converts it into `md_replay::Pacing`: `Fixed` when no windows, a validated `PacingSchedule` otherwise (overlapping/inverted/out-of-order windows refuse startup). Pacing only changes release delay; every frame is still processed. See [[replay#Pacing driver]].

## Session hot loop and record routing

[[crates/datafeed/src/session.rs#step]] is the one batch body for every venue: reap a frame batch, tap and feed each frame, route the drained events, publish. A venue adds no runner or glue module.

[[crates/datafeed/src/session.rs#run]] loops `step` until the source closes, and a [[session#Pull-based feed session]] runs it once per poll, so the binary, a host, and the tests share it.

It takes the adapter as `&mut A` with `A: md_pipeline::DynAdapter + ?Sized`, so a concrete adapter (tests) and the binary's boxed `dyn DynAdapter` run the same body. The erased path costs two indirect calls per frame (`feed`, `drain_into`); session, sink, and clock stay monomorphized. The caller keeps the adapter, so a live reconnect reuses it, and `run` returns `(SessionStats, source)`: the exhausted source stays inspectable (for example `BinaryFileReplay::io_error`), while live reconnects retain all book, derive, OHLCV, trade-memo, telemetry, and tap state through the [[crates/datafeed/src/session.rs#SessionState]] the caller passes. Batch size and the stop flag travel together in [[crates/datafeed/src/session.rs#RunControl]].

Per batch, every frame is tapped raw, fed with its own `frame.stream()` and `frame.venue_seq()`, and drained into one `Vec<MarketEvent>` the session allocates once and reuses, recording a `(stream, end)` span per frame. Routing then walks the events in emission order, publishing each on the stream of the frame that emitted it, so a second-channel record leaves on stream 1 from a `DualLiveSource` or an interleaved `CaptureReplay` alike. The adapter picks its decoder by stream and ignores a stream it does not declare (replay refuses such a frame first, see [[session#Config-wiring rejections and replay failure surfacing]]). [[tests#Two-stream test adapter#Per-stream feed and publish]] runs frames on three streams through `run` and checks which records publish where. Feeding the whole batch first is safe because an adapter's output does not depend on when it is drained; only the raw-tap interleaving coarsens to batch granularity, which the capture format never observes (each row carries its own `ts_recv`). A tap failure stops feeding at that frame, but the frames tapped before it still route and publish before the error returns, so a fault mid-batch loses no record already captured.

[[crates/datafeed/src/session.rs#route_events]] probes each MBO's book lines through the engine's read-only `prefetch_mbo` eight events before it routes, so those cache misses resolve behind routing work. The lookahead crosses frame boundaries. Order, and therefore egress, is unchanged.

[[crates/datafeed/src/session.rs#route_event]] advances the OHLCV watermark to `event.header().ts_event` first, so non-trade traffic closes due bars on time. Consecutive MBOs from one source event (same venue, instrument, `ts_event`, `ts_recv`, `venue_seq`) apply as one segment, and a segment always flushes at its frame's end. [[crates/datafeed/src/session.rs#route_record]] routes everything else: `Level` publishes as it is, `Trade` and `TradeBreak` on stream 0 drive VWAP, OHLCV, and the trade memo while those on any other stream publish as they are, `Control` feeds [[crates/datafeed/src/restart.rs#RestartState]] before publishing, and the remaining kinds publish as they are. Every venue routes a kind identically; NASDAQ's `Control` reaches `RestartState` too, a no-op since NASDAQ never emits `RecoveryComplete`.

An order-flow `Mbo` is the level book's only writer. A `Level` is the wire-authoritative price level a venue publishes on a separate market-by-price channel, so the session publishes it on its own stream and neither applies it to `BookEngine` nor derives an MBP10/BBO from it. Applying it would corrupt the shared aggregate: a `New` adds on top of the depth the order flow built at that price, and a `Change` or `Delete` overwrites it, so a later order `Cancel` reduces a level that no longer matches its resting orders. [[crates/datafeed/src/session/tests.rs#level_event_publishes_without_writing_the_book]] routes an order add, then `New`, `Change`, and `Delete` levels at its price, then the cancel, and checks the best bid after every step plus the published record kinds.

Stream 0 is also the only source of the shared trade aggregates: OHLCV bars, the `DeriveEngine` VWAP, and the trade memo ([[crates/datafeed/src/session.rs#SOURCE_STREAM]]). It is a single-channel venue's only stream and a dual-channel venue's primary channel. The session does not read it from the descriptor: the `venue.rs` unit test `every_venue_leads_with_the_aggregate_stream` requires every built-in descriptor to declare it first, so a venue leading with another id fails the suite before its trades can publish without feeding a bar. A secondary channel may reprint executions on stream 1 under its own trade id, an id space apart from the primary feed's `MatchNumber`. Folding those in would count each execution twice, and a secondary `TradeBreak` whose trade id equalled a primary match number would reverse the wrong print. A `Trade` or `TradeBreak` on any other stream therefore publishes and nothing more. [[crates/datafeed/src/session/tests.rs#second_stream_trades_publish_without_feeding_aggregates]] routes two stream 0 trades, their stream 1 reprints, and a stream 1 break by secondary trade id that matches a primary match number, and checks the open 1s bar, the VWAP, and the memo after every step plus what was published.

The runner reads only the shared `AdapterStats`; a counter an adapter keeps beside it has no reader in the binary.

The session runs under one [[crates/datafeed/src/session.rs#DefaultVenuePolicy]] for any venue: permissive book gate, full purpose set on every board, printable-gated tape. Board-to-purpose routing and per-venue book gating are policy-authoring work outside this wiring layer (see [[orderbook#Policy seam]]).

### Graceful shutdown

A live session finishes its capture on SIGINT/SIGTERM instead of truncating it. A sync signal handler sets a shared stop flag the hot loop polls at each batch boundary.

`main.rs` registers SIGINT and SIGTERM against the process-wide [[crates/datafeed/src/shutdown.rs#flag]] before the runner starts; the handler only stores into an `AtomicBool`, safe from signal context, so the sync hot loop (which yields to tokio only during connect) still observes it. [[crates/datafeed/src/app.rs#run_config]] hands that flag to a live session through [[crates/datafeed/src/feed.rs#FeedSessionBuilder#stop]]; a replay keeps a never-set flag of its own and runs to the end of its capture. The session checks the flag after each routed batch, never mid-batch, so a frame is never half-processed. On set it flushes the open OHLCV bars and ends as if the source had closed, and `run_config` stops polling. `run_config` closes the session on every exit, graceful or not, and `SinkSession::close` ([[crates/datafeed/src/feed.rs#SinkSession]]) finishes the capture: a connect, session, or replay fault (an undeclared stream, a retained io error) also closes writers and writes manifests before the error propagates, and a fault wins over a close error, which is logged. A stop arriving during reconnect backoff or a connect attempt aborts promptly (each poll waits at most 50ms of a backoff and checks the flag first, and a hung dial is dropped), so shutdown stays bounded even when the venue is down.

### Live adapter anchor roll

A live session with an unset (`0`) `session_midnight_ns` installs each trade date's anchor on the adapter from frame receive time, so `ts_event` stays an epoch instant across date rolls for a venue whose wire carries time since midnight.

NASDAQ's wire carries only time since the venue's midnight, and the adapter adds it to one anchor. Replay resolves that anchor once from the capture date (see [[capture#Capture header reconcile]]); live has no header, so [[crates/datafeed/src/session.rs#SessionState#from_config]] builds an [[crates/datafeed/src/anchor_roll.rs#AnchorRoll]] for a live source with an unset anchor. [[crates/datafeed/src/session.rs#run]] checks it before each feed: a frame received at or past the cached session end opens the session holding its `ts_recv` through [[crates/datafeed/src/session_window.rs#resolve_session]], the tap's own window rule, and calls `set_session_anchor` with that session's start before the frame feeds. The cached end starts at `0`, so the first frame always installs an anchor, including after a reconnect that rebuilds the adapter and its session state. Per frame the cost is one `Option` check and one `u64` compare; zone lookups run once per trade date. A frame the session model cannot place (an unknown zone) ends the session with `SessionError::AnchorUnresolved` before it feeds, and the frames fed before it in the batch still route and publish.

`LiveFeed::new` ([[crates/datafeed/src/live.rs#LiveFeed]]) refuses an explicit nonzero `session_midnight_ns` when the session builds, as [[crates/datafeed/src/wiring.rs#build_tap]] refuses a set `taps.capture_date`: a live run has no end date, so a fixed anchor would decode every frame after the first roll on the wrong day. `from_config` still leaves an explicit anchor alone and never rolls it, for a library caller that drives [[crates/datafeed/src/session.rs#run]] itself. Replay never rolls: its `ts_recv` can be synthetic (`base_ts + n * step_ns`), so the capture header's date is the only trustworthy anchor there and the seam parity digests stay as they were. A venue whose wire carries absolute time ignores the call, since `set_session_anchor` is a provided no-op ([[pipeline#Venue adapter seam]]).

The roll follows receive time, so a prior-date frame received just past the session end decodes on the new anchor. NASDAQ rolls at New York midnight, outside trading hours, so this is accepted. A venue that trades across its roll would need the wire's own date signal.

[[crates/datafeed/src/session/tests.rs#live_unset_anchor_installs_at_first_frame_and_rolls_at_session_end]] runs one batch through a recording adapter and checks that the session start goes in before the first frame, nothing goes in inside the session, and the next date's anchor goes in right before the frame at the end. [[crates/datafeed/src/session/tests.rs#explicit_anchor_and_replay_never_install_one]] and [[crates/datafeed/src/session/tests.rs#unplaceable_live_frame_ends_the_session_unfed]] cover the explicit, replay, and unknown-zone cases, the `live` unit test `live_session_refuses_a_set_session_anchor` checks the live refusal against an unset control, and the `anchor_roll` unit test `rolls_across_new_york_spring_forward` steps the tracker across NASDAQ's 23h 2026-03-08 session.

### Atomic MBO source-event publication

One adapter drain is one wire-event boundary; contiguous same-instrument MBO rows mutate completely before any derived L1/L2 view is visible.

Each session owns one reusable two-row-capacity buffer. [[crates/datafeed/src/session.rs#route_mbo_segment]] applies every row to `BookEngine`, then calls `DeriveEngine::apply_mbo_batch` once against that applied book to read one final MBP10/BBO off its depth ([[orderbook#Derive engine#Atomic MBO batches]]), publishes all MBO rows in adapter order, then publishes the final MBP10 and BBO. A non-MBO or instrument change flushes the segment without changing established Fill/Trade/Status ordering.

The observable replacement order is `Cancel(old)`, `Add(new)`, final MBP10, final BBO. Both MBO rows retain their source timestamps and non-zero `venue_seq`; `EgressSequencer` assigns distinct gapless `egress_seq` values. [[tests#Order book reference parity]] checks this order against reference L1 to L3 state.

### Derived views, OHLCV, and trade breaks

Each `Mbo` segment feeds `DeriveEngine`, publishing the derived `Mbp10`/`Bbo` pair after its records; a `Level` derives nothing. Every routed record advances the per-session `OhlcvEngine` watermark; a stream 0 `Trade` also folds into its OHLCV bars.

An attributed `Fill` is published as its own normalized record beside `Trade`; it does not feed the anonymous book mechanics or OHLCV a second time.

`BookOutcome.suspect` (from a `Gate::Flag` policy hook) ORs `RecordFlags::SUSPECT` onto the source record's header before publish; `ApplyResult::UnknownOrder` increments a per-instrument counter on `SessionStats.unknown_order_counts`, the maybe-bad-book telemetry.

`OhlcvEngine` tracks a configurable set of bucket widths, defaulting to the seven sub-day intervals (1s, 1m, 5m, 10m, 15m, 30m, 1h) and overridable via the `ohlcv_resolutions` config field or a `--ohlcv-resolutions` CLI flag. Bars close on a monotonic event-time watermark: each routed record's `ts_event` advances it and flushes any bar whose window has elapsed, and session end flushes the rest, so an illiquid or last-of-session bar still prints. Each closed `Ohlcv` carries its `resolution` and publishes on the stream of the record that closed it, right before that record and before any `Mbo` segment an earlier event left buffered; the end-of-session flush publishes on stream 0. A stream 0 `TradeBreak` reverses both `OhlcvEngine`'s still-open bar and, via a bounded session-local `trade_ref -> (price, qty, instrument)` lookup (`DeriveEngine` keeps no such memo of its own), `DeriveEngine`'s running VWAP accumulator.

[[crates/datafeed/src/session/tests.rs#closed_bar_publishes_before_its_closer_on_its_stream]] routes a stream 0 trade, a buffered add, a stream 0 `Status` that closes the trade's 1s bar, a second trade, and a stream 1 `Status` that closes that one, then checks the egress order and streams.

## Pull-based feed session

A host builds a [[crates/datafeed/src/feed.rs#FeedSession]] in code and pulls records from its own loop. The binary runs a [[crates/datafeed/src/feed.rs#SinkSession]], which publishes in place, so both share one step.

[[crates/datafeed/src/feed.rs#FeedSessionBuilder]] starts from a venue descriptor and a `SourceConfig` and sets the rest of the session's settings: venue id, session anchor, capture taps, OHLCV resolutions, and a stop flag. It needs no file on disk; `From<DatafeedConfig>` is the binary's path from a loaded file. A file's `sink` and `observability` keys stay with the binary, because a host takes records from `poll` or passes its own sink, and the library installs no metrics recorder. `build` returns a `FeedSession`, and [[crates/datafeed/src/feed.rs#FeedSessionBuilder#build_with_sink]] returns a `SinkSession` over any `OutputSink`. Either runs the MDC1 capture-header reconcile, builds the tap, and opens a replay file or checks a live dial. A live source dials on the first poll, on a tokio runtime the session owns with one worker, which only drives connect and login. [[crates/datafeed/src/live.rs#DialRuntime]] runs each dial on a scoped thread of its own and shuts the runtime down in the background on drop, because `Runtime::block_on` and a blocking runtime drop both panic on a thread inside an async runtime, such as a host's `#[tokio::main]` thread. A host may therefore poll, close or drop a session inside its own runtime; a blocking poll then holds that runtime's thread.

`SinkSession::poll` ([[crates/datafeed/src/feed.rs#SinkSession]]) takes one step and publishes what it routes into the session's sink: one frame batch through [[crates/datafeed/src/session.rs#step]], one dial, or one slice of a live reconnect wait of at most 50ms. The replay and live feeds and the egress sequencer are generic over the sink, so nothing is boxed or copied on the way. Once the source ends a poll returns `FeedError::Closed`, or the fault that ended it once and then `Closed`; the records routed before the end are already in the sink. A paced replay sleeps each frame's pacing delay inside the call, and a live dial blocks until connect and login finish or time out.

A `FeedSession` wraps a `SinkSession` over its record queue. [[crates/datafeed/src/feed.rs#FeedSession#poll]] appends at most `max` records to the host's `Vec` and returns the count; `Ok(0)` means nothing is ready yet. With nothing queued it first takes one step of its `SinkSession`. Records routed past `max` stay queued, and the session steps again only once the queue is empty, so the queue holds at most one batch. When the source ends, the remaining records drain first, the closing OHLCV flush included. A fault that ended the source then returns once, after the records routed before it, as the batch runner publishes them before its error; the session holds that end until the records are out. Every later poll returns `FeedError::Closed`.

`SinkSession::close` ([[crates/datafeed/src/feed.rs#SinkSession]]) takes the session by value and finishes the capture tap, returning its error, so no poll can follow a close; `FeedSession::close` goes through it. Dropping a session without `close` leaves the open capture file unfinished. Neither session is `Send`: the adapter is a `Box<dyn DynAdapter>`, and replay shares its egress clock through an `Rc`.

[[crates/datafeed/src/app.rs#run_config]] builds a `SinkSession` over the configured sink (`Null` or `Collecting`) from the loaded config and polls it until `Closed`.

### Owned records

[[crates/datafeed/src/record.rs#OwnedRecord]] holds one stamped record inline: its `RecordHeader`, a body buffer sized to the largest record, the body length, and the stream, 488 bytes in all.

[[crates/datafeed/src/record.rs#MAX_RECORD_LEN]] is `Mbp10`'s 480 bytes, header included, and every record type the session publishes is const-asserted to fit. `bytes()` returns the header and body as one run, the bytes a C host will receive; a const assert pins the body right after the header. The body buffer is `MaybeUninit`, and only its first `body_len` bytes are written, so a record costs the copy of its own bytes and no fill of the rest.

A `FeedSession`'s sink is a queue of these records, owned by the egress sequencer, which lends it only by shared reference, so the session reaches it through a `RefCell`. For one step the queue lends the host's `Vec` to the sequencer, so each record is written once, straight into the slot it takes in the host's `Vec` (`Vec::push_mut`, then the body copy). Records past `max` are then copied into the queue's own buffer, and later polls drain them. A copy allocates only when a buffer grows. Over the NASDAQ reference fixture that is zero heap allocations per record, where a `Vec<u8>` per record costs one.

### Host handoff bench

`benches/feed_session.rs` times both sessions against the batch runner, which publishes in place, in ns per published record.

All three passes replay the vendored NASDAQ order-book reference fixture, repeated 1,000 times, from memory, unthrottled, batch 64, into a sink that only counts, with a fresh session per round. The sink session pass polls until `Closed`, as [[crates/datafeed/src/app.rs#run_config]] does. The host pass polls with no cap, then publishes each record through `as_record_ref`. Rounds rotate which pass goes first, every round checks that all passes published the same number of records, and the bench prints the median of each pass and of each session's paired difference against the runner. It has no baseline and no regression test.

On `m4pro-macos` on AC power (2026-11-26) the medians were about 50 ns per record for the runner and the sink session, a paired difference between -0.11 and -0.01 ns, and about 63.5 ns for the host poll, +12.3 to +13.0 ns. Before the sink session, the binary polled a `FeedSession` and copied each record twice: 89 to 92.6 ns per record, +44 ns against the runner. The runner itself reads 44 to 46 ns in a binary built from the earlier library and 49 to 51 ns in one built from this one, its own code unchanged, at every environment padding from 0 to 4,096 bytes.

## Pipeline stage observability

Feature-gated (`observability`, default off) per-stage latency and throughput timers. A default build compiles them out; with the feature on the runtime gate still defaults off until a config turns it on, so a normal deployment is unaffected.

`src/obs.rs` is the seam: `stage_timer`, `record_records`, and `init` each have a no-op twin under `not(feature = "observability")`, so [[crates/datafeed/src/session.rs#run]], [[crates/datafeed/src/session.rs#route_mbo_segment]], and [[crates/datafeed/src/session.rs#publish_record]] call them unconditionally with no `cfg` scattered on the hot path. Four named stages record into separate `metrics` histograms: [[crates/datafeed/src/obs.rs#STAGE_FEED]] (`adapter.feed`, parse plus normalize), [[crates/datafeed/src/obs.rs#STAGE_BOOK_APPLY]] (core `BookEngine` apply) and [[crates/datafeed/src/obs.rs#STAGE_BOOK_DERIVE]] (`DeriveEngine` reading MBP10/BBO depth off the applied book, timed apart from apply so the derive read is attributable on its own), and [[crates/datafeed/src/obs.rs#STAGE_EGRESS]] (stamp and publish). The book timers sit in adjacent, non-nested scopes in `route_mbo_segment`, both firing once per MBO segment, so their means share a denominator. The adapter fuses parse and normalize with no decode-only entry, so the timers cannot separate the two; the decode-only pass of [[session#Pipeline stage observability#NASDAQ pipeline bench]] does.

[[crates/datafeed/src/config.rs#ObservabilityConfig]] turns the gate on and selects a [[crates/datafeed/src/config.rs#MetricsExporterConfig]] (Prometheus pull or OTLP push); [[crates/datafeed/src/app.rs#run_config]] calls `init` inside the tokio runtime so the exporter's background tasks attach there. The runtime gate lives in `observability_core`, which the crate takes as a direct dependency and flips itself. The SoupBinTCP client and `transport-core` take it from the same root manifest entry, `observability-core`; `observability` brings its own copy from the tag on the root `observability` entry. Both entries carry the same url and tag, so cargo builds one copy and a single flip arms the session timers and the client's recv metrics. A change to one entry without the other links two copies, each with its own gate. The crate's `observability` feature forwards to `client-soupbintcp/observability` for that reason.

### NASDAQ pipeline bench

`benches/nasdaq_pipeline.rs` reads the stage timers over a capped prefix of a local full-day NASDAQ ITCH 5.0 capture and reports throughput and latency per stage.

It needs the `observability` feature and a capture git does not track, so CI does not run it. The target sets `harness = false` and owns its replay loop, so one run covers 100,000,000 messages and reports hdr percentiles per stage. The capture comes from `NASDAQ_ITCH_SAMPLE` and opens the way [[crates/datafeed/tests/support/reference_parity.rs#open_binary_sample]] opens it: zstd or gzip into `BinaryFileReplay`, with `ts_recv` counting up from zero. [[crates/datafeed/benches/nasdaq_pipeline/passes.rs#Capped]] closes the source after the cap, so every pass replays the same prefix. The cap is [[crates/datafeed/benches/nasdaq_pipeline.rs#DEFAULT_MAX_MESSAGES]] unless `BENCH_MAX_MESSAGES` sets another. On the 2020-01-30 capture it ends at 10:35:23 exchange time, after the pre-market, the open and the first trading hour. A read error inside the prefix fails the run, because it would end the replay early like an end of file.

Each run makes three passes:

- Decode only: [[crates/datafeed/benches/nasdaq_pipeline/passes.rs#decode_only_pass]] runs the length check and `itch_v5::parse_match` that `NasdaqAdapter::feed` runs before it normalizes. [[crates/datafeed/benches/nasdaq_pipeline/visitor.rs#DecodeVisitor]] reads every field of every view through `black_box`, because views decode on access and a visitor that ignored them would time dispatch alone. Each batch's decode loop is timed as a unit and the result is a mean, `stages.parse_mean_ns`. One decode takes about 6 ns, less than the 42 ns tick of the monotonic clock on the baseline host, so percentiles per message would show only the tick.
- Native throughput: [[crates/datafeed/benches/nasdaq_pipeline/passes.rs#session_pass]] calls [[crates/datafeed/src/session.rs#run]] on a boxed `dyn DynAdapter` built from `NasdaqAdapter::new`, with `NullSink`, `NoopTap`, a `SharedClock` and batch 64, the batch the binary's replay runner uses. No recorder is installed yet and the metrics gate is off, so each stage timer costs one gate load. Its wall time gives `throughput.msgs_per_sec`.
- Instrumented latency: the same call after `main` installs [[crates/datafeed/benches/nasdaq_pipeline/recorder.rs#StageRecorder]] and turns the gate on. The four stage histograms give count, mean, p50, p90, p99, p999 and max, and each stage also reports one mean per 1,000,000 samples. `stages.normalize_mean_ns` is the feed mean minus the decode mean. The wall time of this pass includes the timers' own cost and is not reported.

A stage timer resolves its histogram in the recorder on every drop, before it reads the clock, so that lookup is inside each sample. `StageRecorder` keeps it to four string compares and one `Arc` clone. `obs` is a private module, so the recorder repeats the four metric names, and `main` fails a run in which a stage recorded no sample. That catches a renamed metric and a second linked copy of `observability-core`, whose gate the bench would not have turned on.

Stage samples cover different populations, named in each stage's `unit`: feed per message, book apply and book derive per MBO segment, egress per published record. Their means therefore do not add up to a cost per message. On the baseline host every sample is a whole number of clock ticks.

The report is JSON ([[crates/datafeed/benches/nasdaq_pipeline/report.rs#BenchReport]]): venue, host (`label` from `BENCH_HOST`, `cpu` from `BENCH_CPU`, arch, os, logical CPUs), capture (path as given, sha256 of the file, `max_messages`, `messages`), batch, layout, throughput and stages. A run writes `benches/results/nasdaq_metrics.json` under the crate, which git ignores, or the path in `BENCH_OUT`. [[tests#Bench timing]] covers the committed baseline and the test that compares a run with it.

#### Stack position and window means

A run's speed can depend on where the process stack starts, so the report records that position and one mean per 1,000,000 samples of each stage.

On the baseline host a 16-byte access to a stack slot is slow when a 16 KiB page boundary falls in its middle. `book_derive` keeps two depth arrays on the stack whose 24-byte rows are written with 16-byte stores, and the book derive stage is slow at ten stack positions 48 bytes apart in every 16,384 bytes. In runs capped at 10,000,000 messages its p50 and p90 are 83 or 84 ns at five of them, where a boundary splits a row of the bid array, and its p50 is 42 with a mean of 32 to 37 ns at the other five, in the ask array, against a p50 of 41 and a mean of about 29 ns elsewhere. Other frames on the per-message path have accesses of the same kind at positions of their own, some outside every timed stage. The stack pointer at `main` moves 16 bytes for each 16 bytes of environment and arguments, address randomization moves it by whole 16 KiB pages, and two runs with a byte-identical environment can still start 16 bytes apart.

[[crates/datafeed/benches/nasdaq_pipeline/report.rs#Layout]] holds the low 14 bits of two addresses, taken with [[crates/datafeed/benches/nasdaq_pipeline/report.rs#low14]]. That is the offset in a 16 KiB page, which address randomization on the baseline host leaves alone. `stack_low14` comes from a local that `main` declares as its first statement and passes through `black_box`, which keeps the local in `main`'s frame. `adapter_low14` comes from the boxed adapter of the instrumented pass, a heap address that [[crates/datafeed/benches/nasdaq_pipeline/passes.rs#session_pass]] returns.

[[crates/datafeed/benches/nasdaq_pipeline/recorder.rs#StageSamples]] keeps a running sum and count per stage beside the hdr histogram. Every [[crates/datafeed/benches/nasdaq_pipeline/recorder.rs#WINDOW_SAMPLES]] samples it stores the mean and starts again, so `window_means_ns` has one entry per full window in arrival order and a partial last window has none. The recorder receives a sample after the stage timer's end clock read, so no sample includes the sum. When a stage changes speed partway through a run, the means show a step, and the percentiles of the whole run mix both speeds in one distribution. Each stage reports the window size as `window_samples`.

A comparison of two builds starts both with the same small environment, checks that the reports show the same `stack_low14`, and keeps that value where every frame from `main` down lies inside one page, about 5,300 to 14,400 on the baseline host. The bench does not compute a class. A `stages.book_derive.p50_ns` of 41 goes with a level derive stage and 42 or more with a raised one, and the stage figures alone cannot rule out a position, since part of the affected code is outside the timed stages.

## Sinks

Stamped records leave the process through an `md_pipeline::OutputSink`; the session is generic over it so the choice never boxes on the hot path.

[[crates/datafeed/src/sink.rs#NullSink]] drops everything (the binary's default when no downstream is wired); [[crates/datafeed/src/sink.rs#CollectingSink]] retains records for tests to assert against. [[crates/datafeed/src/config.rs#SinkKind]] selects between them from config (`Null` default, `Collecting` for capture-only/test mode); [[crates/datafeed/src/sink.rs#AnySink]] is the enum `wiring.rs` selects at assembly time. Real cross-process sinks (shared memory, network) land later and slot in behind the same `OutputSink` trait with no session change.

## Typed library errors

The run entry points ([[crates/datafeed/src/app.rs#run]] and `run_config`) and the feed session (`FeedSessionBuilder::build`, `FeedSession::poll` and `close`) return [[crates/datafeed/src/error.rs#FeedError]], so a host branches on the variant, not message text.

Lower-level entry points return the inner error directly: `session::run` returns `SessionError`, the `source::connect_*` functions return `SourceError`, and `AnyTap::finish` returns `CaptureTapError`.

`FeedError` is `#[non_exhaustive]`. `Config` wraps [[crates/datafeed/src/error.rs#ConfigError]] (unreadable or invalid config, a capture header that contradicts the config, a retired or misplaced tap setting, a venue and source pair with no dial). `Source` wraps [[crates/datafeed/src/source.rs#SourceError]] (live connect and SoupBinTCP faults, replay open, decode and retained io faults, a row on an undeclared stream). `Session` wraps `SessionError` from the hot loop, `Tap` is a capture close failure, `Runtime` is a tokio runtime or a live dial's thread failing to start, `Observability` (feature `observability`) is the pipeline failing to install, and `Closed` is what `poll` returns once the source has ended and every record is out.

Source chains survive except for the retained replay fault: `SourceError::RetainedIo` copies only the `kind` and `message` of the held `io::Error`, so its `source()` is `None`. `main.rs` prints the error with `Display`. Four messages carry a prefix the old boxed errors lacked: `read config <path>: `, `open replay <path>: `, `tokio runtime: ` and `observability init: `. `ConfigError::UnsupportedSource` names the source by its config `kind` tag (`live`, `live-dual`, `replay`) and never carries the source config, because the config holds SoupBinTCP credentials.

## Config-wiring rejections and replay failure surfacing

`nasdaq` with `SourceConfig::Live` fails before dialing: [[crates/datafeed/src/live.rs#live_dial]] finds no dial for it and `LiveFeed::new` ([[crates/datafeed/src/live.rs#LiveFeed]]) returns `ConfigError::UnsupportedSource`, so it never runs against the wrong protocol.

NASDAQ live is MoldUDP, with no SoupBinTCP session, and its descriptor sets `soupbin_live: false`, so it matches neither the `Live` arm (one SoupBinTCP stream) nor the `LiveDual` arm (two). For the `Binary`/`BinaryGz` replay formats, `replay.rs` checks `BinaryFileReplay::io_error()` on the source once the replay ends (reached through `PacedSource::source()`); a retained io error (corrupt or truncated gzip mid-stream) fails the run instead of exiting success on a silently-truncated tail. `Capture` replay has no such check (`CaptureReplay` carries no retained-error state). It is the only container that tags rows with a stream, so [[crates/datafeed/src/replay.rs#DeclaredStreams]] wraps it: the first row on a stream the venue's descriptor does not declare closes the source, the rows before it still publish, and the run fails naming that stream. Without it a single-stream venue's capture holding a stream 1 row would replay to a clean end with those rows missing, since an adapter ignores an undeclared stream without counting it.

Further wiring-time refusals: `Eager` load with a `Capture`/`Pcap` container, `Auto` detection hitting an unrecognized file, an invalid pacing window list, and a multi-stream venue's replay on any non-capture container.

## Restart and resume seam

[[crates/datafeed/src/restart.rs#RestartState]] tracks the resume points a reconnect needs: a SoupBinTCP sequence, a Glimpse sequence, and one captured socket sequence per leg of a dual source.

The SoupBinTCP `next_expected_sequence` is captured after a source closes; the Glimpse `RecoveryComplete` resume sequence is captured when the session routes the drained `Control` record. `resume_login_config` prefers the socket sequence, then Glimpse, and falls back to sequence-1 replay when neither exists. For a dual source, [[crates/datafeed/src/restart.rs#RestartState#capture_dual_resume]] records each leg's own `next_expected_sequence` when a dual session returns, and [[crates/datafeed/src/restart.rs#RestartState#resume_dual_login_configs]] builds one login config per leg with the same preference order, since the primary and secondary legs run independent SoupBinTCP sequence spaces.

[[crates/datafeed/src/live.rs#LiveFeed]] redials after `Closed` for the single and dual source shapes, and keeps the adapter, [[crates/datafeed/src/session.rs#SessionState]], capture tap, and `EgressSequencer`. A source closes on end of session, on a transport close, on a session error, and on a heartbeat timeout (see [[session#Live and replay IngestSource swap#Heartbeats and server silence]]). The new login requests the captured resume point, and downstream `egress_seq` remains one monotonic sequence across every socket lifetime. A bounded backoff (`live.rs` `ReconnectPacer`, 100ms doubling to a 3.2s cap) paces reconnects after sessions that closed without delivering frames; one poll waits at most 50ms of it and checks the stop flag first, so a pending reconnect neither blocks a poll for long nor holds shutdown.

[[crates/datafeed/src/source.rs#connect_tcp_resuming]] and [[crates/datafeed/src/source.rs#connect_dual_resuming]] take the descriptor's declared stream ids (one, or primary then secondary) and keep them across every redial, and retry a rejected resume from sequence 1. When the server rejects the resume or accepts it at sequence 1, `live.rs` rebuilds the adapter through the descriptor's `make` and resets engine state for deterministic replay while retaining capture and egress continuity. A mixed dual acceptance (one leg resumed, the other forced back to 1) drops the connected source and redials both legs at sequence 1, so no leg prefix is lost against reset engines; requesting sequence 1 outright is likewise treated as a full replay. Both connects take the stop flag and abort promptly on shutdown, returning `None` when a dial to a down venue is dropped, so a stop during a hung connect does not stall the finish.

No venue adapter in this workspace emits `RecoveryComplete` or decodes two streams. [[tests#Two-stream test adapter]] checks the routed `Control` reaching `RestartState` through a test-only adapter. The `restart.rs` and `source.rs` unit tests and the dual cases of [[tests#Live session against a mock server]] cover the rest of the Glimpse path and the dual resume.
